1 · THE OPAQUE-HANDLE / PERMUTATION RESULT

The handle is minted at instantiation as the claim that authorized the member plus an ordinal, and it is
carried in the **existing** field: a member's `elementId`. So `container[handle].leaf` now addresses a member
exactly as it already addressed a derived element, and nothing new was introduced. A member's entailment
address is for the first time a real element path rather than a display string, because an index was never
resolvable.

The falsification case passes, and I made sure it is not passing vacuously. Part one permutes the two
indiscernible teams and **asserts the vacuity** rather than reporting a pass: with all represented values
equal the members differ only by handle, so exchanging them is the identity operation and proves nothing.
Part two is the one with teeth — it forces genuinely asymmetric per-member values in, 4 against one handle
and 8 against the other, then exchanges handles and values together. Every value follows its handle, every
verdict is identical, and **the coach-facing text is literally identical**.

Fourteen guards hold the boundary. Four of them exist because tracing found attack paths I would not have
predicted:

- **The handle must be a string.** The fidelity layer walks the game and treats every finite number it finds
  as a quantity the game supports. A numeric handle of 777 made an instruction claiming the quantity 777 pass
  as supported — it silently defeats the invention check for that number.
- **It must be additive.** Re-minting derived element ids instead of only member ids produced 17 fidelity
  violations as the provenance join between the status record and the game collapsed.
- **The discriminator must be unconditional**, even where a claim owes one member. A mint yielding the bare
  claim id would make a member findable by the element lookups driven from the derived record, so a member's
  leaf could stand in for a derived element's in the acceptance checks — a false PASS rather than a failure.
- **It must stay out of class-id space.** Reference identity grades a string HELD if it equals a class id, so
  a handle used verbatim as one would let an authored string target a handle. Keeping the `realized:` prefix
  preserves your guard; a handle string instead grades DANGLING, which is the right answer.

And a guard against an ordering that nothing enforced: no source may sort by a handle, parse it, or recover
the ordinal from it. That is checked across every file rather than trusted.

4 · WHAT ACTIVATING COMPARES ACTUALLY CHANGED

`comparison.ts` implements the register's own thirteen-key block rather than deciding anything: the form and
its six operators, the two operand forms, the rule that a comparison takes no line and never entails a value,
evaluability that is never quietly true, and the limit that an assumed comparison may report but never fail
authoritatively. Comparisons are evaluated at post-realization — the earliest stage where a per-member
operand has a subject — and reported as their own kind rather than as a gate clause, because the register
says a comparison takes no line.

**What became expressible.** A comparison whose operands each resolve to exactly one element is now
evaluated, in both directions, and that is new: before the handles there was no way for an operand to pick out
one instantiated member.

**Prose matching is gone.** GF2-14.b carries its equality as a typed comparison, and the roster reads the
declared relationship. That removes the defect class rather than the symptom — prose is no longer consulted
at all, so an item reading "unequal between the teams" cannot license an equal division by matching a
substring. The roster still derives 6 and 6. A regression test asserts the "unequal" item declares no
comparison.

**What stayed authoring-limited, and the reason is the register's own.** Both operands of that equality name

    "No aggregate function is named (each, some, the sum, the greatest) for a comparison ranging over

So the equality is **declared and REFUSED** — reported, never counted as holding. Naming the two members
individually is not open either, because no knowledge item may target a handle, which is your guard. **This
corrects something I told you**: I said symmetric per-team claims need no identity because a set-level
comparison expresses them. Under the canonical mechanism that is not available — the set-level form is
exactly what `stillOpen` refuses. So the mechanism you told me to use requires the identity you authorized.
The two rulings fit together more tightly than I realised.

**The four stale fitNotes are corrected**, each citing AM-16 and each naming the real residual blocker instead

6 · THE REPRODUCIBILITY QUESTION YOU ASKED ME TO ANSWER

You asked whether there is a technical reason an internal deterministic enumeration is insufficient, before
introducing a content-derived distinction between indiscernible members.

**There is not, and I have not introduced one.** The ordinal is reproducible from the realization input: the
order members are placed in is the order the input lists them, and that order is part of the input's bytes.
Same input, same handles.

What is **not** sufficient is the audit trail, and this is a real finding rather than a quibble. The
realization record stamps itself with the *resolved game's* input digest, so it does not cover realization's
own order-dependent decisions — two different realizations of one resolved game carry the same stamp. The fix
for that is to extend the digest to cover the realization input, which is a separate and smaller thing than
distinguishing the members. I have not done it, because it is outside what you authorized today.

So: the handle is minted from the ordinal and is deliberately **readable** rather than hashed. Hashing would
have obscured the audit trail to buy opacity that the guards and the permutation test already enforce.

I should also flag the one place the boundary is weaker than I would like. The ordinal is textually present in
the handle, so opacity is enforced by test rather than by construction. I think that is the right trade given
what you said about not introducing a content-derived distinction, but it is a convention backed by a check
rather than an impossibility, and you should know that is what you have.
