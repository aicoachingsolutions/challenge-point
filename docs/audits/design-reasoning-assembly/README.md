# Design reasoning: the bounded A05 activity-assembly experiment

**Standing.** Review evidence only. Offline. Not served to coaches, not an authorization, not approved wording, not a selection input.

- **What it is.** Christian authorized "a bounded, offline, review-only activity-assembly experiment for A05 Progress the Attack" in his second reply of 5 November 2026 (received 5 November 2026; filed in the sources repository as `sources/2026-11-05-assembly-authorization/originals/christian-reply-to-dimensions-review.txt`). This folder records what was built, what it shows and how it was checked.
- **The honest answer, in one paragraph.** Against his 28 October test ("without requiring a fully authored activity-specific version"), the answer is No. The review pathway's code routed A05 to its context from the approved planning model, resolved the Game Problems from his scoped ruling for A05 (the planning model's translation for A05 is unpopulated), found three compatible Game Forms without ranking them, and confirmed that the scoring event is one of the context's approved scoring events. It configured nothing. Of the 52 values the activity rests on, 7 are read from knowledge by code and 42 were entered by hand in a labelled record written for A05 (15 stated in his words, 4 of them only through his 23 October principle that the Laws apply by default; 19 illustrative; 8 our own readings); 3 are left unresolved, with no value. Three more values are recorded beside the activity but are not part of it (the two scoring-condition texts and his coach-feedback question): 55 in all. His six classes over the 52 activity values: class 1, 1; class 2, 12; class 3, 9; class 4, 0; class 5, 19; class 6, 11 (3 unresolved and 8 of our readings). The coach text is a DRAFT template fill keyed to configuration paths, not the production renderer and not approved wording. With nothing added, the same build would serve Secure Possession. Part 1 of the report is titled "the activity as assembled", never "as generated".
- **What it changes.** New files in `back/src/system/design-reasoning/`; the stated edits to five existing files in that folder; one entry in `back/scripts/unit-tests.json`; one `npm` script in `back/package.json`; this folder. Nothing on the live route or A01's checked pathway imports the folder.
- **What it does not do.** No knowledge file, workbook, sport-module file, contract, approved wording, authorization record, realization-choices index, planning model, or Stage 1/2 rulings file is edited. No configuration step, no production relevance join, no live routing change, no width change, no new element-to-affordance relationship.
- **Quotation marks.** Double: his words or approved knowledge, verbatim. Single: ours.

**To run.** From `back/`: `npm run design:assembly` writes `evidence/assembly-report.txt` and `evidence/assembly-results.json` (it reads `evidence/regression-record.json`, which Part 5 prints, and runs the mutation loop, whose counts the front and Part 5 print); `npm run design:assembly -- --out <dir>` writes elsewhere (the regression record is still read from this folder). The tests are `src/system/design-reasoning/assembly.unit.ts` (30 test functions: items (a)-(y) of the design, the value-phrase table (c2), display-text invariance (k2), his words' pinned hashes, the requirement account and the wording's scope), in `npm test`. Test (v) requires the committed report and results to equal the runner's output, so the runner must be re-run after any change to the code, the record, the wording or the regression record.
