# Design reasoning: the isolated reusable configuration handoff

**Standing.** Review evidence only. TEST-ONLY. Isolated: nothing a coach or an administrator can reach runs it. Not deployed. Not merged: the branch `claude/reusable-config-handoff` has no pull request, and the standing auto-merge practice does not apply to it. Not an authorization, not approved wording, not a selection input. Christian authorized it in Christian's first reply of 7 November 2026 (received 7 November 2026; filed in the sources repository as `sources/2026-11-07-handoff-authorization/originals/christian-reply-to-reusable-configuration-proposal.txt`): "This authorization is for an isolated development pathway only." and "You may reuse and extend existing code where necessary, provided the new behavior remains unavailable to live coaches and does not change the existing application or A01's checked behavior."

**Quotation marks.** Double: Christian's words, verbatim. Single: ours (labels, record text, values, code).

**How to read the coach text.** 'wording APPROVED' means the sentence is, word for word, one of Christian's approved coach sentences; it says nothing about the standing of what it states (its class). 'wording DRAFT' means words that are not approved. The renderer's status words: DERIVED, required by the selected knowledge and worded as a requirement of the game; STARTING, where this activity starts (a value chosen inside authored bounds, an alternative taken, or a preferred default), said as a fact about this activity and adjustable; COACH_CHOICE, left to the coach and put to the coach as a choice.

## What the handoff is

The review pathway's Steps 1 and 2 (the resolved context and Game Problems; the Game Form result) handed to the checked configuration and rendering chain (`buildActivityUnderAuthorizationRecords`, the TEST-ONLY entry), case by case, with no separately hand-authored activity record. In Christian's four verbs:

- **Receive** a case: the Learning Goal; Step 1 and Step 2, run by the handoff, never copied from data; the case's inputs (session, Christian's words and how each enters the chain, illustrative values and TEST-ONLY treatments, each labelled).
- **Determine** the form: Step 2's SELECTED form, or, where Step 2 leaves compatible alternatives, only a form the inputs name with a stated basis (an illustrative choice a filed ruling permits, or our logical inference), checked among the compatible forms; the others retained with no preference; with no named form the run stops ('alternatives retained; no basis to select'). The chain's own keyword-scorer pick is recorded as not used.
- **Produce**: a TEST-ONLY in-memory record and realization from the case's rulings, the DRAFT store where the context has no contract, choices for open lines, labelled stand-in items, decision 1's review-only wording; the chain builds; the handoff reads back the lines, the sentences with their from-paths, the laws and requirement accounts, the diagram model and any refusal.
- **Preserve**: every line graded by its determining premises (our grading map, in Christian's six classes), every sentence by the lines its from-paths join; decision kinds A, B and C per line (OURS, for Christian's review); refusals, gaps, alternatives, illustrative values and TEST-ONLY treatments listed apart; on every configuration: 'Productive, recurring opportunities to meet the intended Game Problem: not established (no approved relationship ties a Game Problem to any line)'.

A manipulation is placed only on a relationship; today the input accepts only a labelled TEST-ONLY stand-in for one (class 4 'TEST ASSUMPTION', never knowledge), because no representation or reader of approved relationships exists (none is represented for Create Space). What Test B1b shows is therefore the placement and grading path an authorized relationship would take, not that the mechanism reads one. Without a stand-in the manipulation is reported as 'no authorized relationship' and the configuration is unchanged. A value proposed for a line is applied only as an ILLUSTRATIVE supplied choice, never over a line a ruling of Christian's closes (it is then reported as contrary to that ruling). A Game Problem put into the TEST-ONLY record in a test is reported as a mismatch with Step 1, never switched.

This is reusable assembly, not knowledge-authorized selection. Christian's words: "At present, the resolved A05 Game Problems do not determine the activity's environmental configuration through approved Create Space relationships." The evidence keeps that gap visible on every configuration and in Test B2, which swaps the Game Problem and shows the configuration unchanged.

## How to run and regenerate

From `back/`:

- The tests and the evidence check: `node node_modules/ts-node/dist/bin.js --files -r tsconfig-paths/register ./src/system/design-reasoning/handoff.unit.ts` (also in `npm test`). It fails if the committed evidence differs from what it generates.
- Regenerate the evidence: the same command with the environment variable `UPDATE_HANDOFF_EVIDENCE=1` (PowerShell: `$env:UPDATE_HANDOFF_EVIDENCE='1'` first; Git Bash: prefix the command). The evidence is generated twice inside the test and must be identical; no time stamp is written.
- No runner exists: the draft store cannot be loaded by a runner, so the unit test is the only place the mechanism meets the chain.

## Known limitations

- **A05 itself does not generate.** A05-0 (the knowledge as it stands) is refused at structure on the drafted origin and control lines; A05-1 (the provisional state reading as a TEST-ONLY treatment) at structure on the drafted control line alone (its V5 referent item does not exist). Both refusals are RESTATEMENT-ONLY: the lines' elements come from our DRAFT contract items; V6 is owed by our DRAFT contract's own NOT_AUTHORED (type=origin), and V5 only by restated:GF2's NOT_AUTHORED declaration on the row (our CANDIDATE restatement), applied row-wide because our DRAFT contract leaves the control type undeclared (the refusal reading prints, beside each cited line, which declaration owes it). A05-2, the only A05 run that reaches text, is CONDITIONAL on the 13 September verification and is never A05's result.
- **No Game Problem determines any line** (Christian's section 12 gap). Test B2 swaps the record's Game Problem to Gain Access, a candidate, and the configuration is identical.
- **The coach-served end-line restart does not compose from Christian's words** (Test R1, A05-1 and A05-2): the restart's episode line is a line nobody established (the chain decided it row-wide, and its only requirement declaration, our restatement's claim on possession-change transitions, does not reach the restart by the chain's own reach), and no ruling says whether the restart begins an episode. It is a structural refusal, not reported as a refinement. The configurations the chain would serve (A05-2 and the two GF2 structural cases) hold no restart for a ball over an end line: the dead-ball restart policy is not established in any of them, in A05-2 Laws 16 and 17 read not applicable (no goals), and no departure is recorded. Christian's first reply of 7 November, section 5, says a game without conventional goals may require a different end-line restart, as a structural adaptation still to be examined; whether its absence is a foundational blocker is Christian's to place. The restart's exact distance, the coach's location and the delivery need not become canonical knowledge and may stay coach-adjustable (Christian's first reply of 7 November, sections 7 and 8); the second reply, section 5, adds that exact restart locations should not delay core generation unless they present a material structural, safety or representative-integrity problem. With a diagnostic TEST ASSUMPTION for the episode line, the build stops at communication: the checked renderer names no coach as taker and has no served-ball phrase. No engine feature and no DRAFT restart sentence were built; the restart is described in the report only, and its items are graded by Christian's own label for it (illustrative), not by the basis the realization gate requires of them.
- **A record cannot authorize one manipulation alone** (Test B1c): selection refuses (no compatible combination; the selection's size and role-mix rules are the engine's, with no ruling of Christian's cited for them). An applied manipulation is therefore placed in the selection explicitly, as the form is, and the record's authorized set is left as ruled. The placement bypasses bounded selection (whose record route refuses, B1c) and the live route's check that refuses a served constraint no record authorizes; every later stage still runs, and no check is widened. With the Wide Zone Advantage placed, the chain would serve the text and withholds the checked coach diagram (its rule D0: a channel width the coach chooses within a range is not drawn at one size). The variable target condition does not compose with GF2 here (refused at structure on our restated items).
- **No representation or reader of approved relationships exists** (none is represented for Create Space): the input accepts only a TEST-ONLY stand-in, so 'applies once authorized' is shown for the placement and grading path only. A smallest next step: a representation of an approved relationship (context, Game Problem, manipulation) and a reader that hands it to the handoff in place of the stand-in. Not built.
- **The starting condition read as the state of the attack has no structural carrier**; it is carried only as the labelled withholding of the origin items.
- **The kick-off's centre mark has no register row**: the law's adaptation is owed and reported under the TEST-ONLY realization's REPORT check, held by the test to our DRAFT classification; Test E3 shows the hold refusing at validation when the law is not procedural under the classification it holds to.
- **The illustrative zone depth** enters as two stand-in items, which the chain treats as authored; the ILLUSTRATIVE label is the handoff's, printed on every sentence citing the zones' depth.
- **GF4 still does not generate** (Test C2): after decision 2 it stops at structure on its trigger reachability alone (RESTATEMENT-ONLY: the failing check names GF4's I06, our restatement; the items its teams would rest on, I10 to I12, are assumptions of our restatement). The four GF4 goals stop earlier, at knowledge (their contexts have no contract; Test C3, and D02 in C4); our 6 November proposal said 'at the structural check'.
- **The two other goals whose form Step 2 selects GF2** (Test C4, each run as D02 is: Step 2's form, production records only). TA02 stops at knowledge (its context, RPC-003, has no contract among the production records); with the TEST-ONLY draft store, labelled DRAFT, it stops at structure on the same two drafted lines as A05-0 (RESTATEMENT-ONLY). A02 stops earlier, at selection: it has no production record, and the chain's own bounded selection refuses on GF3 (no compatible combination; the shaping role unfilled) before the handoff can place the form Step 2 selected, so the knowledge stage is not reached.
- **Decision 2's limits.** Decision 2 changed only the checked chain's restatement (`corpus-restatements.json`). The live generation route's use of GF4's example text (`activity/build-activity-skeleton.ts`, lines 242 to 245, which passes the example incentive patterns to the generator) was neither examined nor changed, and changing it is not authorized. GF4's team-size claim (row P2), which rests only on the example I13 ('e.g. 4v6'), is left unchanged: decision 2 covers incentives only.
- **The structural cases run through a vehicle** (the TA02 DRAFT record with its context removed), because the TEST-ONLY entry takes only a Learning Goal request, and **the chain would serve them only under a TEST ASSUMPTION** (TT-LAW-11-STAND-IN: a TEST-ONLY classification with the law of offside procedural, neither our reading nor a ruling of Christian's). Without it, our DRAFT classification (offside MATERIAL) refuses them at validation, and with no classification the fail safe refuses them on the kick-off and offside laws (measured in Test C1). Christian's no-offside ruling is scoped to A05's initial small-sided realization and is not generalized to them.
- **The refusal reading** names, for each cited line, the item that establishes its element, with its class; for an open line refused for being outside its permitted set (a reason saying the value is not one of the permitted alternatives) whose bounding items the chain names, those items, with the element's item named as not bounding it (Test B3: the chain names its narrowing item GF2-03.b, our restatement of the DRAFT soccer module, so B3 reads RESTATEMENT-ONLY; GF2-03.e, Christian's ruling item, establishes the element and does not bound the line); an open line cited for any other reason is read through its element (Test B1c's V17). The chain's words are kept apart from ours: its line verdict NOT_AUTHORED means nothing authored the line's value, and its reason 'declared gap' is not our gap. The gap rule is ours: a cited owed line is listed as a line nobody established (a gap) when no requirement declaration (NOT_AUTHORED, EXCLUDED or CLAIMED) the chain decided it over reaches the line's element class by the chain's own reach function (`derivation/reach.ts` `reaches()`) and the chain's own scope rule; a requirement counts as reaching when its scope reaches the class (an own-involvement declaration reaches only the classes its own object forms) and that function does not answer FALSE, as the chain's classification keeps a requirement in force (undetermined is never rounded to false; measured: Test B1c's variable target region line has two requirement declarations the function answers UNDETERMINED, so it is cited, not a gap). `classify.ts` exports neither its requirement kinds nor its scope rule, so the handoff copies them, and Test E4 holds both copies to `classify.ts`'s source text; measured there, the evidence's owed lines meet 5 own-involvement declarations, all of the element's own object, so applying the scope rule changes no reading. Every other cited owed line prints which requirement declarations reach its element (which declaration owes it). For a refusal met before any game exists (at structure or realization) the build returns no game, so the unit test runs the chain's own derivation again on the input the build derived from (build-activity's input assembly replicated in the test only) and reads nothing unless it reproduces the build's reasons word for word (at structure the Gate A reasons, at realization the realizer's reasons); otherwise the test fails. Configuration lines hold position terms, not extents, so 'lines identical' in Test A4 covers the terms' values only; an extent no stand-in declares is not graded (the chain does not name the item it comes from).
- A sentence's class covers only what its from-paths cite: in GF2 on lines, 'Each team defends one line and attacks the other...' says the target noun without citing the noun lines, so its class 2 overstates it (the noun is our realization choice, class 6). The live renderer is not changed.
- Some A01 from-paths (layout marks and zones) join no line and are printed as such; the purpose's approval evidence is data checked only against the planning row's 'Active' cell. The secondary Game Problem's requirements (Exploit Space) are neither carried into the TEST-ONLY record nor evaluated by any line, so they are not satisfied; they stay visible.
- The evidence is compared byte for byte with LF line ends; the folder's `.gitattributes` holds it to LF on checkout, as the Stage 2 and assembly evidence folders are held.
- Decision 2's change is in a file `build.js` copies into `dist/knowledge`, and decision 1's hook is in the bundle: the live bundle is not byte-identical to main, and isolation rests on the branch staying unmerged and undeployed. The behaviour snapshot against main (391 entries) is the behavioural proof.
